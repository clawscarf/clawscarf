# Deployment internals

This guide maps the implementation behind the [installation CLI](installation.md).
Use `clawscarf configure` to create or change an installation; users do not construct
internal input JSON or invoke the component operators separately.

## Lifecycle

The [configuration schema](../../scripts/deployment/configuration.ts) defines the
internal input generated by the CLI. Mutations run under the installation lock in
[state.ts](../../scripts/deployment/state.ts).

| Operation   | Implementation and responsibility                                                                                                                                                                                                         |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prepare     | [prepare.ts](../../scripts/deployment/prepare.ts) validates inputs, creates private credentials and owned Docker resources, runs database migrations, and initializes an empty runtime home. Repeated preparation preserves native edits. |
| Start       | [launch.ts](../../scripts/deployment/launch.ts) starts the controller, selected model/browser services, OpenClaw and forwarding, then Access. It checks readiness before returning.                                                       |
| Stop        | [launch.ts](../../scripts/deployment/launch.ts) closes application entry first, stops the owned OpenShell runtime, then stops Compose services. Data remains.                                                                             |
| Reconfigure | [reconfigure.ts](../../scripts/installation/reconfigure.ts) handles explicit changes to retained settings using the component operators. Ordinary startup does not reapply presets or rotate credentials.                                 |
| Delete      | [delete.ts](../../scripts/installation/delete.ts) verifies ownership and removes this installation’s containers, volumes and networks. It never prunes other projects.                                                                    |

Docker Compose owns the controller, forwarding and companion service lifetimes;
OpenShell owns the protected OpenClaw container. No ClawScarf host daemon is installed.
Closing the terminal leaves services running. Interrupted startup retains services and
data for inspection, resumed start or explicit stop.

## Stored data and credentials

The public `--directory` is the installation directory. Deployment operators receive
its internal `state/` subdirectory. Keep both the directory and its Docker volumes.

| Location               | Contents                                                                                                                      |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Installation directory | Saved configuration, selected runtime tools, source credentials and retained pack files.                                      |
| `state/`               | Installation identity, internal input, generated Compose configuration, allocation records and private service configuration. |
| `state/controller/`    | OpenShell controller identity, certificates and state.                                                                        |
| Owned Docker volumes   | OpenClaw’s `/home/node`, Access PostgreSQL, and selected model-database/browser state.                                        |

The runtime’s persistent home contains native configuration, workspaces, identities
and credentials. Gateway, shell commands and local tools share this filesystem;
per-agent workspace paths remain native OpenClaw configuration. Initialization runs
only on an empty owned volume and disables Docker’s image-to-volume copy.

The controller alone mounts the Docker socket and controller signing key. Its state
mount uses the same absolute host/container path because Docker resolves OpenShell’s
supervisor executable on the host. On Linux, the controller runs as the installation
owner with Docker socket-group access; bundled LiteLLM uses the installation owner’s
UID to read its private files. Forwarders receive only client credentials.

Access mounts its own explicit configuration and runtime database credentials, not
database-owner or controller credentials. Migrations run during preparation, never
on API startup. Private management TLS is separate from browser-facing TLS; its CA
is not installed in the workstation trust store. Retained data is not a backup.

## Ownership and recovery

[Preflight](../../scripts/deployment/preflight.ts) checks executable files and listener
ports. An occupied port is reusable only when the exact running service belongs to
this installation. Port checks do not reserve listeners against other processes.

[Networks](../../scripts/deployment/networks.ts) uses Docker’s allocator for separate
companion and runtime bridges. Docker 29’s `0.0.0.0/24` allocation chooses a free subnet
while allowing fixed service endpoints. Optional browsing adds isolated browser and
node-machine bridges. Allocation records retain exact IDs and ownership labels;
foreign, replaced or ambiguous resources are rejected.

[Runtime allocation](../../scripts/deployment/runtime.ts) records intent before
creation and reconciles lost responses against the owned runtime. Incomplete inventory
or uncertain absence never triggers blind reallocation. Startup verifies the runtime’s
actual image and exact writable home mount through
[runtime-binding.ts](../../scripts/deployment/runtime-binding.ts) before opening Access.
These are startup checks, not continuous monitoring.

If an operation reports an uncertain outcome, inspect its private records and the
controller before resuming. Do not delete records to force a retry. Interrupted
configuration and runtime replacement block ordinary startup until resolved.
Diagnostics retain structured failure reasons without logging credentials or raw
subprocess output.

## Team profile

Hosted login and company OIDC use the same internal `team` profile. Application and
widget origins must differ. HTTP is accepted only on loopback; public/LAN origins
require HTTPS with a certificate covering both names and a matching private key.
OIDC secrets and TLS keys must be private regular files owned by the operator.
Only application and widget listeners can publish beyond loopback; management,
PostgreSQL, controller and native forwarding remain local.

The CLI handles hosted registration or the private first-administrator claim. A health
probe establishes service availability, not successful OIDC login or administrator
authority. Access owns admission and revocation; OpenClaw owns native roles.
See [login configuration](installation.md#login-and-administrator) and the
[Access contract](../../services/access/README.md#configuration-and-operation) for
callbacks, identity claims and enrollment. DNS, host firewall rules and public
certificate issuance/renewal remain the operator’s responsibility.

## Models and Connections

[Model preparation](../../scripts/deployment/models.ts) retains the selected model
configuration, runtime-scoped key and optional private CA. The
[model gateway](../../scripts/deployment/model-gateway.ts) prepares bundled LiteLLM;
external LiteLLM uses the same native provider contract. OpenShell policy allows the
runtime’s Node process to reach the selected endpoint; TLS remains verified. Provider
keys and gateway master keys stay outside OpenClaw. See [model configuration](../models/README.md).

### Activate Connections

Use [Connections configuration](installation.md#connections) through `clawscarf configure`.
The CLI registers the selected cloud service and delivers separate management and
runtime credentials. The companion receives the management credential; OpenClaw
receives the scoped execution credential and broker endpoint. Provider keys, catalog
data and account records remain cloud-side.

[Connections preparation](../../scripts/deployment/connections.ts) retains endpoint
and trust material; [reconfiguration](../../scripts/installation/reconfigure.ts) handles
explicit enable/disable changes. Native changes preserve unrelated settings. An
interrupted change requires observation and explicit resumption. Enabling the
capability does not link an external account; users do that in native Connections.

## Shared browser

When selected, Compose runs Chromium, its native browser node, restricted DNS and
network services. Chromium has an isolated network and retained team browser state.
Startup checks authenticated CDP readiness, then pairs and waits for the native node
before opening Access. Stop/start preserves team cookies and logins.

The browser proxy permits public HTTP/HTTPS and blocks private destinations; it is
not a domain allowlist. See the [browser network](../execution/network/README.md) and
[native node](../execution/browser-node/README.md) for topology and credentials.
The [upstream routing issue](../execution/browser-node/README.md#upstream-browser-routing-bug)
remains unresolved.

## Runtime upgrade

[upgrade.ts](../../scripts/deployment/upgrade.ts) replaces stopped OpenClaw compute
while retaining its home volume. It does not upgrade the controller, companion or
database, and it provides no backup or rollback. Published-version upgrades remain
an open decision in [TODO.md](../../TODO.md#upgrade-decision).

For development, `clawscarf upgrade --help` describes the command. It requires exclusive
operator control, a stopped installation with only its controller running, an exact
replacement image supporting the startup gate, and the pinned
[Python SDK environment](../../packs/README.md). The operator snapshots controller
policy/settings, replaces compute, restores settings and leaves the result stopped
before normal startup. It does not reinitialize native identities or workspaces.

Resume an interruption with the same image and command. Conflicting settings or
unconfirmed deletion/allocation require inspection, not replay. Native deletion has
no atomic UUID precondition, so concurrent external controller changes are unsafe.
Provider bindings are retained references, not copies of provider credentials.

## Testing changes

Run the [repository checks](../../scripts/README.md). For real Docker boundaries,
use the opt-in [platform installation test](../../tests/deployment/platform-live.test.ts).
[Allocation](../../tests/deployment/allocation-live.test.ts) and
[replacement](../../tests/deployment/upgrade-live.test.ts) tests deliberately interrupt
operations; their source files specify required inputs and disposable state.
Those fixtures can retain resources for inspection: delete them after testing.
[Release results](../../release/README.md#build-and-publish) belong in the release guide.
